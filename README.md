# Puppet profiles [![Build Status](https://github.com/cultuurnet/puppet-profiles/actions/workflows/ci.yml/badge.svg)](https://github.com/cultuurnet/puppet-profiles/actions?query=workflow%3ACI)

## Description

The profiles puppet module bundles useful, site-specific functionality in
meaningful classes that can be applied to systems.
This module is thoroughly unit tested (acceptance tests are coming), to make
inevitable larger refactoring less painful.

Profile classes can be arbitrarily nested, and this is highly recommended, to
prevent them from becoming large conglomerates of resources.


## EKS authentication to private Vault

`profiles::vault::eks_clusters` consumes the Hiera metadata exported by Terraform
into `publiq-configdata/terraform/role-vault/eks-<environment>-<cluster>.yaml`.
The existing Puppet role-based Hiera hierarchy discovers and hash-merges those
files. The parameter defaults to an empty hash, preserving existing Vault setup.
The EKS resources are managed only when Vault is running with auto-unseal enabled,
after the existing secrets engine, policy and authentication setup.

Example input, normally generated by Terraform:

```yaml
profiles::vault::eks_clusters:
  publiq-testing:
    environment: testing
    oidc_issuer_url: https://oidc.eks.eu-west-1.amazonaws.com/id/<issuer-id>
    auth_mount: eks-publiq-testing
    role_name: external-secrets
    bound_audiences: [vault]
    bound_subject: system:serviceaccount:external-secrets:vault-reader
```

Each cluster gets its own JWT auth mount, role and `eso-<cluster>-read-only`
policy. Vault trusts that cluster's issuer, validates the exact service-account
subject and audience, and issues a 10-minute token with only that cluster's
policy. No default policy or static Kubernetes/Vault token is added.

The policy environment comes from the exported `environment` field, not the
Vault server's Puppet environment or the cluster name. Only `acceptance`,
`testing` and `production` are accepted; missing or wildcard values fail catalogue
compilation. A testing cluster may read `puppet/data/testing` and its descendants,
and read/list `puppet/metadata/testing` and its descendants. It cannot read other
environments, list the mount root, modify secrets, destroy versions or administer
Vault. Only self-token lookup, renewal and revocation are additionally allowed.
Production and acceptance follow the same pattern for their respective paths.

Configuration files contain only public metadata and policy definitions under
`/etc/vault.d/eks`. Exec guards compare the live policy/configuration/role on every
run so remote drift is repaired without needing a local file change. Existing
certificate authentication and its policies are unaffected. No Vault API restart
is required for these settings.

ClusterSecretStores, service accounts and the Vault server CA inside Kubernetes
remain separate deployment work. Vault needs outbound HTTPS to the EKS OIDC
issuer, and each cluster needs private connectivity to Vault. The Kubernetes API
CA and token reviewer credentials are not needed for this JWT login method.

Removing a Terraform metadata entry stops declaring it; it does not automatically
revoke an existing Vault mount or policy. Explicitly remove the retired cluster's
`eks-<cluster>` auth mount (which revokes its issued tokens) and its
`eso-<cluster>-read-only` policy as part of decommissioning. This profile does not
purge unrelated Vault auth configuration.

Validation:

```sh
bundle exec rspec spec/classes/vault_spec.rb spec/classes/vault/eks_spec.rb spec/defines/vault/eks_cluster_spec.rb
```

The rendered policies were additionally checked against a disposable loopback-only
Vault for all three environments, including denied reads across environments,
write/delete/version-destruction denial and permitted self-token operations. The
local smoke harness is not part of this repository. Live Vault was inspected only
to confirm path names; no live changes were applied.
